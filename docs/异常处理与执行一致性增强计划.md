# Code Agent 异常处理与执行一致性增强计划

## 一、目标、范围与实施顺序

在已经完成的六阶段 Harness 基础上，补齐异常判断、后台核对、诊断和可信验证能力。继续使用标准 `create_agent`、LangGraph 消息状态、PostgreSQL Checkpointer、原生 middleware 和既有 Task／Run 调度。

实施分为三个批次，每批独立迁移、测试和验收：

| 批次 | 前置条件 | 主要交付 | 为下一批提供什么 |
|---|---|---|---|
| 第一批：异常契约与诊断 | 当前阶段六基线 | 错误分类、回执校验、状态守卫、结构化日志、未决摘要 | 稳定的故障表达和状态更新规则 |
| 第二批：后台核对与清理 | 第一批验收通过 | 有界查询恢复、取消窗口处理、期限预留、清理收敛 | 可供最终发布依赖的可靠操作事实 |
| 第三批：验证基础与错误循环控制 | 第二批验收通过 | 可信验证扩展、可选完成门禁、验证持久化、重复错误拦截 | 后续代码审查与修复功能的接入基础 |

确定以下边界：

- 保持直接修改注册工作区，失败后不自动回滚。
- 保持异常 Run 不自动重放，未知 Task 不自动恢复。
- 不默认增加模型重试、写工具重试或备用模型。
- 运维只增强诊断，不增加主动核对 CLI、人工结果覆盖或强制解锁接口。
- 验证首版提供基础入口和合成验证器，不实现真实测试、Lint 或构建检查业务。
- 不建设 Saga、Outbox／Inbox、消息总线、通用重试引擎、审批平台或新的工作流系统。
- 沿用当前框架锁定版本，本轮不升级 LangChain、LangGraph、MCP 及相关执行框架。

## 二、跨批次共同契约

### 1. 保持四类事实独立

| 事实 | 权威来源 | 不可推导出的结论 |
|---|---|---|
| Agent 执行结果 | Run 状态及明确发布的 checkpoint | 不证明代码已修复 |
| 后台操作结果 | 原容器或原远程句柄的可信观察 | 不证明资源已经释放 |
| 资源清理结果 | 对原资源身份的清理确认 | 不证明外部副作用已撤销 |
| 验证结果 | 服务端注册的可信验证器 | 不覆盖取消、失租或未知操作 |

最终状态仍由既有 PostgreSQL 发布事务决定。网络请求、模型调用、验证器执行均不得放进数据库锁或事务中。

### 2. 最小异常信息

保留现有 `error_code`，增加版本化、可选的 `failure_info`，包含：

- `code`：稳定错误码。
- `category`：参数、权限、传输、超时、协议、执行、配额、配置、持久化、清理或验证。
- `effect`：未派发、已执行但可能有部分效果、执行效果未知、或不适用。
- `recovery`：修正参数、重新读取、重试观察、核对原操作或停止。
- 有界且脱敏的说明。

分类由可信执行代码产生，不接受模型或远程自由文本指定恢复动作。

标准工具继续返回 `ToolMessage`，必要诊断放入 artifact；不建立新的工具结果协议。工具消息由原生 checkpoint 保存，不新增逐调用持久账本。

### 3. 发布与恢复原则

- 请求幂等、原始工具调用去重和业务操作幂等分别解释，不宣称任意 Shell 或 MCP 工具具备“恰好一次”语义。
- 查询、清理与重新启动是不同操作，分别制定恢复规则。
- 重试数据库提交确认不得重新运行 Agent、后台启动或验证器。
- Task 终态不被迟到结果恢复；迟到的可信事实可以完善操作记录和清理状态。
- 新增执行策略进入配置绑定指纹；默认未启用的扩展保持既有绑定兼容。
- 各批次只创建当批实际使用的字段，不提前建设空表和占位框架。

## 三、分批实施内容

### 第一批：异常契约与诊断

**目标：准确表达发生了什么，并为第二批恢复判断提供稳定依据。**

#### 实施内容

1. **收敛错误分类。**复用现有异常类和原生控制异常，集中维护必要映射。取消、失租、配额、Hook 契约错误和持久化故障继续具有控制语义，不能被普通工具错误处理中间件吞掉。
2. **保留副作用的不确定性。**命令非零退出、MCP `isError`、HTTP 错误不能统一解释为“没有执行”。已派发写操作的超时、协议异常或无法解析响应，按真实派发阶段保留可能效果或未知结果。
3. **严格校验关键回执。**使用现有 Pydantic／JSON Schema 能力补齐本地后台回执的类型校验，拒绝将布尔值当退出码、错误类型当标志位，以及不完整结果。复用 SDK 已有 MCP 校验，补充操作归属、结果关联与截断测试，不重写协议解析器。
4. **收敛操作状态守卫。**为既有更新方法明确允许的状态变化、取消优先级和租约条件。普通更新不得覆盖已确认终态；`unknown` 后获得权威终态时，只允许通过核对路径补记事实，不能创建续 Run 或恢复失败 Task。
5. **修复日志字段丢失。**日志格式器输出 Task、Run、operation、agent、工具调用 ID、工具名、耗时、结果类别和错误码。字段采用明确白名单，凭据和完整参数不写入普通日志。
6. **增强只读诊断。**Task／Run 详情及 doctor 提供未决摘要：未知操作数量、未释放资源数量、最老未决年龄、主要原因和关联记录。Task 失败但资源未释放时，明确展示遗留情况。

#### 数据与兼容

新增 `core_0006`，仅为 Run、后台操作和同步外部操作增加可选异常信息。Task 诊断由关联事实聚合，不复制一套操作状态。

旧数据保留原错误码，缺少详情时明确为历史记录未提供；不推测历史副作用。现有提交请求、状态列表和答案字段保持兼容。

#### 本批验收

- 错误分类不能改变原有控制异常语义。
- 错误响应不被解释为无副作用，非法回执不能发布成功。
- 日志字段实际进入输出，脱敏和大小限制有效。
- Task 终态、操作结果和资源清理状态能够分别查询。
- 原有全部测试通过后，才进入第二批。

### 第二批：后台核对与清理可靠性

**目标：容忍短暂观察故障，同时继续禁止不安全重放。**

#### 实施内容

1. **只对明确安全的观察恢复。**首版覆盖 Docker 身份／状态／日志查询、原生 MCP Tasks 状态查询和数据库确认。不自动扩展到所有标记为只读的 MCP 业务工具。
2. **区分瞬时故障与最终未知。**已知资源身份或句柄的短暂连接失败、读取超时，可在预算内再次观察；身份变化、非法回执和协议不匹配立即停止自动恢复。提交响应丢失且缺少可靠句柄，继续按未知处理，绝不重新提交。
3. **持久化观察预算。**复用 `next_poll_at`，增加连续失败次数、首次失败时间、最后成功观察时间和最后观察错误。瞬时故障只更新观察诊断，不提前污染操作主错误码。
4. **采用有界退避。**默认连续观察最多 5 次尝试，失败核对窗口 30 秒；退避基数 1 秒、上限 8 秒并加入抖动，遵守更大的远程轮询间隔。成功观察后清零连续故障计数，Worker 更换不重置未完成预算。
5. **保留未知后的资源核对。**预算耗尽后，操作未知、Task 失败，继续保留占用。已有资源的后续清理观察降低频率，退避上限默认 60 秒；它只能核对或清理原资源，不调用模型、不重新启动任务。
6. **修复取消崩溃窗口。**分别保存取消意图、发送尝试和已收到的确认。每次尝试前查询原句柄。仅当服务端配置明确声明同一句柄取消可安全重复时，允许最多 3 次取消尝试；默认保持单次尝试，取消确认仍不等于终态。
7. **预留清理和发布时间。**保留数据库中的 Run 绝对期限，从 Agent 有效执行预算中扣除实际启用资源的清理上限及默认 2 秒发布余量。模型、工具和后续验证均受有效期限约束；预算不足时停止新动作。
8. **隔离维护故障。**Worker 维护循环对明确的暂时数据库连接故障进行有界退避，并保留停止信号响应。已有 Run 仍受租约约束，失租后按原规则失败，不能因维护重试获得新的执行授权。

#### 数据与配置

新增 `core_0007`，保存观察计数、时间和取消尝试信息。复用第一批异常结构及状态守卫。

MCP 后台工具增加服务端配置 `cancel_retry_safe`，默认关闭并进入绑定指纹。该字段不由 API 请求、模型或远程工具注解授权。

各类恢复只有一个所有者：后台监控负责观察和符合契约的取消；数据库方法负责提交确认；SDK 自动重试保持关闭。摘要继续遵守锁定版本原生行为，不另叠加重试层。

#### 本批验收

- 短暂查询失败恢复后，原操作仍只有一次启动。
- 观察预算、退避和取消次数跨 Worker 更换保持有效。
- 取消意图落库后崩溃，不被误认为服务端已接受。
- 未声明安全重复取消的服务不会收到新增取消重试。
- 取消、Task 超时、身份变化、迟到结果及清理确认丢失均不复活 Task。
- 有限恢复耗尽后，未决事实和占用仍可诊断。
- 第一批接口及测试保持通过后，才进入第三批。

### 第三批：可信验证基础与重复错误控制

**目标：让后续代码修复功能能够接入客观验证，不增加新的 Agent 编排循环。**

#### 可信验证入口

扩展现有受信任 `Extension` 注册，增加可选异步验证器和验证模式：

| 模式 | 行为 |
|---|---|
| 未配置 | 保持现有完成语义，展示未验证 |
| `report` | 记录结果，不改变正常完成状态 |
| `required` | 必须验证通过，才能发布成功 |

验证器通过可信 Python 注册，不从配置字符串动态导入模块。模式和扩展版本进入配置指纹，`required` 未提供验证器时启动即拒绝。

执行位置固定为：

**原生 Agent 返回 → 获取明确最终 checkpoint → 判断是否为最终候选 → 验证 → 清理 → 事务发布。**

- Task 仍有后台操作、未释放资源或未消费结果时，本次属于阶段报告，不运行最终验证。
- 验证器接收可信上下文、候选答案、明确 checkpoint 引用及既有受控资源访问；不能扩大权限、创建后台操作或修改 Agent 状态。
- 结果采用有界结构，状态为 `passed / failed / inconclusive / not_checked`。
- 控制器填写来源 Run、checkpoint、配置版本、验证时间和覆盖范围，模型不能伪造这些字段。
- 工作区验证记录实际观察文件的内容哈希，并在结束时复核；变化则判为无法确认。记录仅证明覆盖的文件，不声称获得全工作区一致快照。
- 首版验证超时默认 10 秒，且不得超过有效执行剩余时间。

`required` 下失败或无法完成分别发布验证失败错误；`report` 下保留真实结果。取消、失租、持久化错误和验证器契约破坏在任何模式下都不能被降级成成功。

不增加最终生成调用，不改写 Agent 原始答案；查询接口中的验证报告是可信验证依据。

#### 验证持久化与发布

新增 `core_0008`，为 Run 增加可选验证报告。Task 查询投影关联 Run 的报告，不建立独立验证工作流表。

报告与 Run 结果、明确 checkpoint、操作消费标记及 Task 状态在现有发布事务中一起提交。发布确认丢失只重试数据库确认，不重新执行验证器。

历史记录展示未验证；只有成功发布并满足所选验证模式的 Run 才能成为后继消息来源。

#### 轻量重复错误控制

通过原生 `AgentMiddleware` 实现，不新增 Planner 或 Judge：

- 仅统计可信执行层产生的参数无效、权限拒绝、文件版本冲突等可修正错误。
- 同一工具、同一最终参数、同一错误码连续出现 3 次时，在下一次模型调用前以 `NO_PROGRESS` 停止。
- 工具调用 ID 不参与指纹；参数修正或成功执行会打断连续计数。
- 普通命令非零退出、有意义的状态查询和文件变化后的测试重跑不按此规则封禁。
- 根 Agent 触发时结束 Run；子 Agent 触发时按受控子任务失败返回父 Agent，保留父任务处理机会。

该机制只拦截明确重复错误，不宣称识别所有语义循环。继续使用原生调用限制、Task 总期限和既有最多五次 Run 的上限。

#### 本批验收

使用合成验证器覆盖通过、失败、无法确认、超时、契约错误和文件版本变化。验证：

- 未配置模式兼容旧行为。
- `report` 与 `required` 对完成状态产生预期影响。
- 阶段报告不误触发最终验证。
- 确认丢失不重复调用模型或验证器。
- 验证失败不进入成功历史、不自动重放或回滚修改。
- 重复错误能停止，合法修正、子 Agent 隔离和正常重跑不被误伤。

## 四、接口、迁移与防返工要求

### 接口变化

- 提交请求继续保持现有严格字段，不允许用户提交恢复策略、验证结论或取消重试授权。
- Run／operation 查询增加可选 `failure_info`。
- Task／Run 和 doctor 增加只读未决摘要。
- 第三批增加 `verification` 查询字段；Task 详情投影来源报告。
- trace 和 timeline 继续复用现有接口；不增加恢复、审批、重跑或人工确认结果 HTTP 接口。

### 防返工约束

- 第一批固定异常信息和状态守卫，第二、三批只能扩展其实际使用，不能各自引入不同错误协议。
- 第二批固定有效执行期限及最终发布边界，第三批验证直接使用该边界，不另建验证调度器。
- 验证门禁使用现有发布事务，不另存一套“业务成功状态”。
- 框架已经负责的消息 reducer、摘要、工具执行循环、checkpoint 和调用次数限制不重新实现。
- 各批迁移只增加当批需要的字段，历史迁移不改写，结构签名、授权和 readiness 同步更新。
- 影响执行的配置变化按既有规则安全拒绝，不为维持在途任务而忽略版本不兼容。

部署仍采用停止旧 API／Worker、owner 迁移、bootstrap、doctor、启动新版本的方式。升级不能自动删除未知记录或释放未确认资源。

## 五、统一验证与交付标准

每批统一执行现有 `python -m scripts.postgres_integration`，使用真实 PostgreSQL、真实隔离 Docker、合成模型及受控 MCP 服务；禁止真实模型和外部 HTTP。

- 保留阶段六现有 245 项测试，新增用例不得以跳过掩盖环境缺失。
- 覆盖发送前、发送后、结果保存前、提交确认丢失、取消发送窗口和租约更换等故障位置。
- 各批执行空库初始化、前一版本升级、重复迁移、历史数据读取及运行角色无 DDL 检查。
- 报告必须非空，零失败、零错误、零跳过。
- 每批更新配置、接口、状态和故障说明，并保留独立验收记录；前一批验收通过后才开始下一批。
- 本计划正文保存到目标文档，后续验收记录回链到该文档。

整体完成标准：系统能够明确区分执行失败、未知效果、资源未清理和验证未通过；短暂观察故障能够在预算内恢复，危险操作不会因此重放；后续代码修复功能可以通过既有扩展接入真实验证，无需改造 Agent 主循环或重新设计 Task 生命周期。
