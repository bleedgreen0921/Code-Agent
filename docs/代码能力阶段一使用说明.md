# 代码分析、只读 Review 与基础修复

本阶段提供 `code-analyze`、`code-review`、`code-fix` 三个自定义 Profile，复用原有 API、Worker、工具循环与执行期限。对应[渐进实施总计划](代码分析Review与修复能力渐进实施计划.md)，自动化证据见[阶段一验收](代码能力阶段一验收.md)。

## 显式启用

[runtime.code.example.toml](../config/runtime.code.example.toml) 是独立完整配置，使用现有默认值补齐未声明项，不与原示例或其他 TOML 合并。不修改内置 Profile 或默认配置加载行为；未加载这份配置时没有三个新入口。

复制为本地配置（例如 `config/runtime.code.local.toml`），替换三个占位值：

| 配置项 | 替换内容 |
|---|---|
| `workspaces[0].root` | 本机实际项目的现有绝对目录 `/ABSOLUTE/PATH/TO/project` |
| `skills.directories[0]` | 本仓库 `agent/project_skills` 的现有绝对目录 `/ABSOLUTE/PATH/TO/agent/project_skills` |
| `execution.image` | 执行镜像构建命令输出的不可变 ID，替换 `sha256:REPLACE_WITH_64_HEX_DIGITS` |

Skill 根目录的直接子目录为三个 `<profile-name>/SKILL.md`。API 和 Worker 都须能读取同一组 Skill 文件。Skill 在启动时加载为只读快照，不作为项目目录挂载进容器。

```bash
# 在 agent 目录，使用已安装 requirements.lock 的 Python 3.12 环境。
python -m scripts.build_execution_image
cp config/runtime.code.example.toml config/runtime.code.local.toml
# 编辑本地副本，填写上述三个值。
export AGENT_RUNTIME_CONFIG=/absolute/path/to/agent/config/runtime.code.local.toml
python -m db.config_check --role agent-worker
python -m scripts.serve --service agent
# 另一个终端使用相同 AGENT_RUNTIME_CONFIG、数据库及既有 Worker 模型配置：
python -m agent_service.worker
```

数据库、模型端点及服务初始化沿用 [README](../README.md)。运行配置只能选择已注册工具，不能填写模型凭据或 Python 扩展。配置检查通过后按既有流程启动；修改配置或 Skill 后停止并同步重启 API 和 Worker，排队任务遇到绑定变化仍按现有 `CONFIGURATION_CHANGED` 规则处理。

示例资源为 1 CPU、512 MiB 内存、128 PID、64 MiB 临时目录，单工具 30 秒，输出最多 16 KiB/200 行。默认使用非 root Worker 的 UID:GID；root Worker 必须显式设置 `execution.user` 为有项目权限的非 root UID:GID。

## 工具和只读边界

| Profile | 工具 | 唯一可读 Skill | 固定 Markdown 章节 |
|---|---|---|---|
| `code-analyze` | glob_search、grep_search、read_file、read_skill、write_todos | code-analyze | 结论；关键代码与调用关系；执行和异常路径；证据与未确认事项 |
| `code-review` | 同上 | code-review | 审查结论；问题清单；审查范围与未确认事项 |
| `code-fix` | 上述工具，加 edit_file、shell | code-fix | 修复摘要；修改内容；检查结果；遗留问题 |

三个 Profile 均必须绑定工作区。分析和 Review 的容器只读挂载项目，编辑与 Shell 不在工具白名单内；这条边界由执行层保证。三个自定义 Profile 均没有委派、项目知识、MCP 或后台工具。Skill 文本不能授予工具权限。

加载这三份 Skill 后，内置 `workspace_read`、`workspace_write` 仍按现有规则可以读取全部已注册 Skill，其既有工具范围不变；它们不受上述三个自定义 Profile 的单 Skill 白名单限制。内置 `chat` 仍为空工具。

分析和 Review 支持指定文件、符号、用户提供的代码片段或变更说明。本阶段没有 Git 差异与历史工具；若需要以差异为范围，应在任务中提供变更说明及目标文件。真实代码引用采用工作区相对路径及读取结果中的行号。未实际执行的分析不能作为已复现或测试通过的证据。

## API 示例

```bash
curl -X POST http://127.0.0.1:8002/v1/runs \
  -H 'Content-Type: application/json' \
  -d '{"task":"分析 src/example.py 中 first_n 的调用与异常路径","profile":"code-analyze","workspace_id":"project"}'

curl -X POST http://127.0.0.1:8002/v1/runs \
  -H 'Content-Type: application/json' \
  -d '{"task":"审查 src/example.py 的 first_n，约定返回前 n 项，重点检查 n=0 与空输入","profile":"code-review","workspace_id":"project"}'

curl -X POST http://127.0.0.1:8002/v1/runs \
  -H 'Content-Type: application/json' \
  -d '{"task":"修复 src/example.py 中 first_n 返回 n+1 项的问题，使用现有测试检查边界；不要改动无关文件","profile":"code-fix","workspace_id":"project"}'

curl http://127.0.0.1:8002/v1/runs/RUN_UUID
```

提交、查询仍使用原有契约，最终内容位于 `result.answer` 字符串。会话在 `POST /v1/conversations` 时选择 Profile 和工作区，后续轮次只提交 task；独立 Task 继续通过 `POST /v1/tasks` 的原有 profile/workspace_id 字段选择。三个 Profile 未启用后台工具，不启动后台工作。完整请求和结果格式见 [API 契约](../contracts/README.md)。

## 修复检查与验证语义

执行环境无网络，依赖必须在镜像准备期提供；任务中不临时安装依赖。项目应预先提供可在工具期限内完成的测试及其运行目录和命令。无外部依赖的 Python 小项目可以使用 `python -B -m unittest discover -s tests -v`；其他项目需自行准备相应镜像和测试入口。

修复通过 read_file 的实际 SHA-256 作为 edit_file 的 expected_hash，发生版本冲突后重新读取。普通测试非零退出会反馈到现有模型循环，可在剩余预算内继续修改。任务不执行 Git 回滚、提交或清理命令；修改直接保留到注册工作区，失败、取消、超时也不回滚。修复 Profile 的 Shell 本身具有写入能力，Skill 中的工作规范不构成命令级拦截器。

最终检查结果应列出真实命令、可获得的退出状态及结果；无法运行、缺失依赖或预算不足时应说明原因。这里执行的测试属于工具反馈，三个 Profile 都**尚未接入可信最终验证**：未配置 verification_mode、验证器或重复错误控制，查询中的 `verification` 为 null；`completed` 只表示原有运行流程成功结束，不表示代码已经通过可信门禁。输出格式和工作方法由提示词与 Skill 约定，不新增格式验证器或重试模型调用。

自动化验收只证明配置、权限和执行链路可用，合成模型的回答不代表真实模型的代码判断能力。Git Review、项目检查增强及可信最终验证分别留到后续阶段。
