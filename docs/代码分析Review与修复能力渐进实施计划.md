# 代码分析、Review 与修复能力的渐进实施路线

## 一、总体目标与实施原则

首阶段同时提供**代码分析、只读 Review、代码修复**三个基础入口，随后逐步补齐 Git 上下文、项目检查和可信完成门禁。

全程复用现有 `create_agent`、原生工具循环、Profile、Skills、Extension、工作区执行及 Task 能力。新增代码主要集中在 Git 只读工具和固定项目检查适配上。

每阶段都形成可单独使用的功能。以功能验收和少量真实任务确认可用性，不建设独立能力评测平台。

## 二、四个实施阶段

### 阶段一：交付三种基础能力

**目标：先让用户能够直接发起分析、Review 和修复任务。**

新增三个自定义 Profile，保持现有内置 Profile 不变：

| Profile | 工具范围 | 主要用途 |
|---|---|---|
| `code-analyze` | 搜索、读取、Skills、Todo | 解释指定代码、追踪逻辑与异常路径 |
| `code-review` | 同上，只读 | 审查指定文件或用户提供的变更 |
| `code-fix` | 上述能力，加编辑和 Shell | 根据明确问题修改代码并运行检查 |

配套三份简短 Skill，固定基本工作方法：

- 分析：先定位实现和相关调用，再说明行为、约束及未确认部分。
- Review：说明问题位置、触发条件和影响；允许没有发现可信问题。
- 修复：先理解和尽量复现，再修改、检查并总结；保护用户已有修改。

采用固定 Markdown 输出，不新增业务状态、报告表或 HTTP 接口。阶段一的 Review 是指定代码审查，Git 历史与变更选择在阶段二加入。

**完成条件：**

- 三个 Profile 均可通过现有 API 使用。
- 分析和 Review 无编辑、Shell 权限。
- 修复能使用现有版本校验编辑与 Shell 完成一个小型缺陷修复。
- 能明确说明实际检查结果和未验证部分，不虚构可信验证通过。

阶段一的独立配置、使用方式和自动化验收分别见[使用说明](代码能力阶段一使用说明.md)与[验收记录](代码能力阶段一验收.md)。本阶段只进行合成模型功能验收，不调用真实模型，不进行效果评测；后续阶段范围保持如下。

### 阶段二：补齐两种 Git Review 模式

**目标：审查当前未提交改动，或从历史中选择某次提交进行审查。**

提供四个薄封装工具：

| 工具 | 功能 |
|---|---|
| `git_status` | 查看暂存、未暂存及未跟踪文件 |
| `git_log` | 返回有界提交历史，供用户或 Agent 选择提交 |
| `git_diff` | 读取工作区变更或指定提交的差异 |
| `git_read_file` | 读取指定提交或暂存区中的文件内容，补充审查上下文 |

两种模式固定为：

- **当前未提交改动**：分别展示暂存和未暂存差异；未跟踪文件列出后通过现有读取工具查看。
- **指定提交**：审查该提交相对第一父提交的变化；根提交与空树比较。合并提交明确标注采用第一父比较。

指定提交的相关代码必须从相同提交读取，避免把当前工作区内容误作历史上下文。

实现约束：

- 在现有工作区容器内调用 Git，不在宿主机直接执行。
- 使用固定参数列表，禁用外部 diff、textconv 和交互行为。
- 不开放任意 Git 命令，不执行 checkout、reset、commit、fetch。
- 接入现有工具授权、只读挂载、期限、输出限制和日志。
- 大输出支持按文件及行范围读取；截断时明确提示，不能声称已审查全部内容。
- 首版要求注册工作区能在容器内直接访问完整仓库；外置 Git 元数据的 worktree／submodule 场景暂不处理。

`code-review` 使用全部 Git 只读工具；`code-fix` 至少加入状态和 diff，用于修改前后核对。暂不扩大子 Agent 工具范围。

**完成条件：**

- 能从历史选择一次提交并完成只读审查。
- 当前改动覆盖暂存、未暂存和未跟踪文件。
- 历史审查不受当前工作区同名文件变化干扰。
- Git 工具不会修改仓库状态。

阶段二的参数、部署及 API 示例见[使用说明](代码能力阶段二使用说明.md)，独立回归证据见[验收记录](代码能力阶段二验收.md)。

### 阶段三：完善项目检查与修复闭环

**目标：让修复过程能够根据真实检查结果继续工作。**

先支持一个小型 Python 项目，使用现有 Shell 执行明确的检查命令。项目说明或 Skill 记录：

- 测试入口和运行目录。
- 必要依赖及执行镜像。
- 常用的目标测试和相关回归命令。
- 允许修改的范围与交付要求。

依赖在镜像准备期安装，不在 Run 中临时搭建环境。初版使用可在现有命令期限内完成的小测试集。

修复仍在原生工具循环中完成：

> 读取与定位 → 尽量复现 → 编辑 → 检查 → 根据失败反馈继续修复 → 核对 diff → 交付

测试断言失败作为普通业务反馈，允许继续修复；失租、环境丢失等控制异常保持原规则。不增加外层修复循环，也不自动重跑已经失败的 Run。

最终说明包括修改原因、文件、执行的检查、结果及遗留问题。该阶段的检查反馈仍与正式 `verification` 报告分开。

**完成条件：**

- 能根据测试失败信息完成一次后续修正。
- 能补充一个暴露旧实现问题的回归用例。
- 能识别测试未执行、环境不可用和实际断言失败。
- 修改范围及用户已有改动能够在交付时说明清楚。

### 阶段四：接入最小可信测试门禁

**目标：为选定项目提供“检查通过才能发布成功”的修复入口。**

新增显式选择的 `code-fix-checked` Profile，保留普通 `code-fix`。通过现有 Extension 注册 `required` 验证器，并可显式开启已有重复错误控制。

最小扩展内容：

- 在验证上下文增加 `run_check(check_id)`。
- 检查 ID、固定命令、运行目录及必要参数由可信 Python 注册。
- API 和 Worker 使用同一可信 Registry 构造入口；配置检查也使用同一注册方式。
- 执行复用原容器、进程收敛、权限和有效期限；不向验证器开放任意 Shell。
- 检查入口要求 Profile 具备对应执行权限，不能给只读分析／Review 入口扩大权限。

首版只接入一组短时间、可离线运行的 Python 检查，不建设通用检查配置系统：

- 执行真实检查并核对结果，不能读取模型写入的通过标志。
- 目标测试必须实际执行；零测试或全部跳过不能通过。
- 必需检查明确失败返回 `failed`；无法执行或超时返回 `inconclusive`；控制异常继续传播。
- 检查定义与候选代码分开管理，固定验收脚本不由 Agent 编辑。
- 对小型验收范围复用现有文件观察与结束复核，检查期间源码变化不能发布通过。
- 检查和复核共享现有验证预算，默认 10 秒；超出预算如实失败或无法确认，不引入后台验证调度。

报告、完成门禁和提交确认全部复用现有实现，不新增数据库表或迁移。较长检查仍可用于阶段三的开发反馈；其可信结果复用留待实际需要时再设计。

**完成条件：**

- 检查通过可以发布成功，失败或无法确认不能成功。
- Agent 仍可在最终验证前根据开发期检查反馈修复。
- 确认丢失不重复执行验证器。
- 未选择检查 Profile 的现有行为和绑定保持兼容。

## 三、接口与框架复用边界

本路线新增内容限定为：

- 自定义 Profile、Skills 和使用示例。
- 四个 Git 只读工具。
- 一个固定项目检查适配及验证访问入口。
- 必要的可信注册、权限和定向测试。

继续使用现有任务提交、消息状态、工具结果、checkpoint、期限、清理和验证报告。首版使用 Markdown 输出，需要机器读取时再采用现有 `response_format`。

本轮不建设 AST 索引、向量检索、代码图谱、多 Agent 协作、补丁管理平台、通用检查引擎或独立效果评测系统。

## 四、验收与推进方式

每阶段先完成配置和定向测试，再通过少量真实模型任务检查使用流程；不以固定成功率作为阶段门槛。

最小场景包括：

- 分析一个函数及其相关调用。
- Review 一段存在明确问题的代码，以及一段正常代码。
- Review 当前改动和指定提交。
- 修复一个可复现缺陷并通过回归检查。
- 检查失败、超时或环境缺失时准确报告。
- required 门禁无法被未执行检查或伪造通过声明绕过。

涉及 Python 执行、权限或验证边界的阶段，运行现有完整集成入口，保留既有测试场景；仅修改 Skills／配置时，进行加载、权限及使用流程检查。

按“一阶段实施、验收、记录后进入下一阶段”推进。第一阶段即可开始日常使用，后续阶段持续增强同一组入口，不反复替换 Agent 架构。
